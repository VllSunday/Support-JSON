# Поведение Support-JSON: что реализовано и что проверяется

Контекст содержит сообщение, доступную историю, правила с id, факты с origin и возможности. Модель возвращает девять полей: category, priority, sentiment, action, recommended_action, reply, missing_info, supported_rule_ids, human_escalation. action задаёт стратегию: ответить, уточнить, предложить операцию или подключить человека. supported_rule_ids — идентификаторы правил, не выдуманные URL.

| Ситуация | Где покрывается | Предел проверки |
|---|---|---|
| Неизвестный необходимый факт клиента | Train, validation, test; HTTP missing_payment_method | Ошибки уточнений остаются возможны |
| Известный факт уже достаточен | Все наборы, HTTP refund_allowed | Отдельно оценивается лишний запрос сведений |
| Отсутствует системное подтверждение | Все наборы, HTTP customer_claim_is_not_system_confirmation | Слова клиента не превращаются в tool_observation |
| Известное решающее условие при другом неизвестном | Расширенный train, AND/OR short circuit | Не доказан перенос на произвольные сложные условия |
| Правила противоречат без порядка применения | Все наборы, HTTP conflicting_rules | Требуется человек |
| Правило разрешает исключение | Test refund_trial_exception: OR, активный trial | Только описанное исключение |
| Клиент просит исключение, которого нет | HTTP exception_not_authorized | Новый validation-derived сценарий, не часть train выбранного адаптера |
| Клиент раздражён, приоритет низкий | Три тона в наборах, HTTP angry_customer_low_priority | Приоритет задаётся политикой, настроение отдельно |
| Те же факты, но изменён порог правила | HTTP same_request_changed_rule | Пара не пройдена: модель отказала и при разрешающем пороге 10, и при запрещающем 9 |
| Сведения только в предыдущем сообщении | history передаётся модели; HTTP customer_facts_available_in_history | Поля решения верны в одном примере, но reply выдумывает внешний статус возврата; в обучении история пустая |
| Операция предложена, но не выполнена | Все gold replies; HTTP proposed_refund_is_not_completed | JSON Schema не обнаруживает ложное утверждение внутри reply; нужен аудит текста |
| Ссылка на использованное правило | Проверка допустимости id и точности множества id | Допустимый id не доказывает правильность толкования |
| Инструмент проверки доступен | Вход capabilities предусмотрен | В первой демке tools=[]; вызовов и настоящих коннекторов нет |

Дополнительные HTTP-сценарии добавлены после начала финального benchmark по вопросу пользователя. Они основаны на validation и изменённых входах. Не используются для изменения весов, промпта или выбора адаптера и не называются независимым тестом новых компаний. Сырые ответы и совпадение ожидаемых полей сохраняются в reports/demo-checks.json; оценка содержательных свойств — отдельно в reports/demo-behavior-review.json.

Режим демки принудительно suggest_only: сервер не выполняет возвраты, отмены и изменения аккаунтов, независимо от присланных capabilities. Для настоящего инструмента нужна отдельная интеграция: проверка прав, вызов API, получение проверяемого результата и повторная генерация с новым tool_observation. Наличие поля capabilities само по себе этого не реализует.

Произвольные правила, нулевые галлюцинации и идеальное выполнение всех перечисленных свойств не гарантируются. Обнаруженный сбой — результат эксперимента, а не повод скрывать сырой ответ или менять оценку.

Итог локальных HTTP-проверок: 12/12 корректных статусов и отклонений плохого входа; ожидаемые поля вместе с контрактом совпали в 8/10 модельных ответов. При отдельном AI-assisted чтении текста отмечены три спорных/неподтверждённых утверждения: ложный отказ при выполненных условиях, изменение включённой границы срока и выдуманный внешний статус возврата. Последние два примера имеют верное структурированное действие. Это отдельная демонстрационная выборка, её нельзя объединять с основным содержательным аудитом test.
