# Промпт для Open Design

```text
Создай детальный визуальный прототип одностраничного веб-приложения Support-JSON в минималистичном тёмном стиле. Это рабочее место оператора поддержки SaaS-сервиса. Макет будет передан разработчику для изменения дизайна существующего приложения.

Назначение продукта
Оператор вводит обращение клиента, правила компании, известные факты и при необходимости историю переписки. Локальная дообученная языковая модель анализирует контекст и выдаёт структурированное решение с черновиком ответа. Правила передаются для каждого обращения, поэтому интерфейс должен удобно показывать и входные условия, и основание решения.
Операции модель только предлагает: возвраты, отмены и изменения аккаунта приложение не выполняет. Ответ проверяет оператор. Синтетические примеры нужны для демонстрации.

Основной сценарий
Выбрать пример либо ввести обращение → проверить правила и контекст → нажать «Разобрать обращение» → изучить решение, ответ и использованные правила. Основные элементы должны быть понятны без обучения интерфейсу.

Компоновка
Небольшой верхний заголовок: Support-JSON, подпись «Разбор обращения по правилам компании», спокойный индикатор «Локальная модель · LoRA».
На широком экране — две связанные области: слева обращение и контекст, справа результат. На мобильном — одна колонка, ввод перед результатом. Области объединены общей сеткой, имеют ясную иерархию и достаточно свободного пространства.

Область ввода
— Компактный выбор синтетического примера.
— Большое поле «Что написал клиент».
— Редактируемые «Правила компании»: список JSON, у каждого правила id и text. Рядом короткая подсказка о возможности изменить правило и сравнить решение.
— Раскрываемый раздел «Факты»: key, value, origin. Источники user_report означают слова клиента, tool_observation — сведения системы; null означает неизвестное значение. Источник факта должен быть различим визуально.
— Раскрываемый раздел «История переписки»: сообщения user/assistant с текстом. Факты и история относятся к текущему обращению.
— Основная кнопка «Разобрать обращение» и понятный статус обработки. Первый запрос может включать загрузку модели.

Область результата
Заголовок «Предложение оператору». В верхней части компактно показать категорию, приоритет, настроение, стратегию, конкретное рекомендуемое действие и необходимость передачи человеку. Использовать понятные русские названия. Настроение и срочность визуально разделены.
Главный акцент — на блоке «Ответ клиенту»: удобный для чтения текст и небольшая кнопка копирования черновика.
Ниже — «Нужно уточнить», если сведений недостаточно, и «Основание решения»: идентификаторы использованных правил и их реальные тексты. Идентификаторы правил не превращаются в выдуманные ссылки.
Раскрываемый «JSON модели»: моноширинный шрифт, переносы строк, отступы, деликатная подсветка синтаксиса и копирование. JSON должен выглядеть как читаемый объект, а не одна длинная строка.
Время обработки — второстепенная подпись. Постоянная спокойная пометка: «Проверьте ответ перед отправкой клиенту».

Визуальное направление
Минималистичный, профессиональный и спокойный тёмный интерфейс. Графитовый фон, чуть более светлые поверхности, тонкие границы, мягкий светлый текст и один сдержанный синий либо бирюзовый акцент. Ясная типографика, основной текст 16–18 px, аккуратные интервалы, умеренные скругления. Цвет помогает понять состояние: critical и ошибки заметны, второстепенные элементы спокойны. Хорошая читаемость текстовых полей, правил и длинных ответов важнее декоративных эффектов.
Избегай неона, тяжёлых градиентов, стеклянных поверхностей, огромных заголовков и обилия отдельных карточек. Это компактный прикладной инструмент: сохраняй текущий сценарий без маркетинговых секций, дополнительных экранов, аналитических графиков и выдуманных интеграций.

Состояния макета
Покажи основной экран с заполненным контекстом и результатом, а также пустой результат, обработку с недоступной кнопкой, запрос недостающих сведений, эскалацию и ошибку JSON/невалидного ответа модели. Ошибка должна ясно объяснять следующий шаг. При изменении входных данных прежний результат становится неактуальным и не должен выглядеть действующим.
Для демонстрационного наполнения используй явно вымышленные русскоязычные обращения без персональных данных. Покажи согласованную пару правил и ответа; демонстрационные числа и ответы не выдавай за реальные измерения качества модели.

Результат
Представь один законченный дизайн-концепт: подробный desktop-макет, мобильную версию, необходимые состояния и раскрытый пример JSON. Добавь краткую спецификацию цветов, типографики, отступов и основных компонентов, чтобы разработчик мог воспроизвести дизайн. Нужен прототип интерфейса, а не новый backend или обучение модели.
```

**Техники:** контекст продукта + ограничения + формат результата — фиксируют функциональность, тёмную стилистику и состав макета для передачи разработчику.
